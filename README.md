# Облачное хранилище

Учебный проект по cloud-file-storage.md.

Стек: NestJS 12 (ESM, Express 5), React 19, Vite 8, TypeScript 6.

## Запуск

Node.js 24, pnpm 11.25.0. Для актуальных генераторов Nest рекомендуется Node.js 24.15+.

```powershell
pnpm install
Copy-Item .env.example .env
pnpm dev
```

Веб: http://127.0.0.1:5173
API через Vite: http://127.0.0.1:5173/api

Пока отображается стартовый React-шаблон. Маршруты API защищены сессией по умолчанию;
без сессии доступны регистрация и вход. GET /api/user/me проверяет текущего пользователя.

## Проверки

```powershell
pnpm build
pnpm typecheck
pnpm lint
pnpm test
pnpm --filter @app/api test:e2e
```

- apps/api — NestJS API.
- apps/web — React SPA.

## Локальная инфраструктура

Запустить Docker Desktop в режиме Linux containers. Добавить в .env переменные
POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB из .env.example.
Они должны соответствовать пользователю, паролю и базе в DATABASE_URL.
Изменение этих переменных не меняет уже созданную базу в volume.

```powershell
docker compose up -d
docker compose ps
docker compose logs -f seaweedfs
```

После готовности SeaweedFS создать бакет один раз:

```powershell
's3.bucket.create -name user-files' | docker compose exec -T seaweedfs weed shell -master=seaweedfs:9333 -filer=seaweedfs:8888
```

Повторное создание сообщает, что бакет уже существует. Посмотреть бакеты:

```powershell
's3.bucket.list' | docker compose exec -T seaweedfs weed shell -master=seaweedfs:9333 -filer=seaweedfs:8888
```

Порты доступны только через 127.0.0.1: PostgreSQL 5432, Redis 6379, S3 8333.
API и React запускаются отдельно через pnpm dev.

```powershell
docker compose stop
docker compose down
```

stop останавливает контейнеры. down удаляет контейнеры и сеть, сохраняя volumes.
Команда `docker compose down -v` удаляет также volumes со всеми данными.
Использовать её только для намеренного полного сброса локальных данных.

## Статус

Инициализирован каркас и настроена проверка env через Zod при запуске API.
Обязательные настройки перечислены в .env.example. Локальный .env не коммитится.
Значения в примере предназначены только для локальной разработки.
PostgreSQL подключён через Prisma 7. Сессии API используют Redis через express-session
и connect-redis. StorageService подключён к S3 и проверяет доступность бакета при старте.
UsersService создаёт пользователей с Argon2id-хешем и проверяет пароли.
POST /api/auth/sign-up регистрирует пользователя и создаёт новую сессию.
POST /api/auth/sign-in проверяет пароль и создаёт новую сессию существующего пользователя.
GET /api/user/me возвращает username текущего пользователя по сессии или 401.
Глобальный AuthGuard закрывает маршруты по умолчанию; sign-up и sign-in помечены @Public().
POST /api/auth/sign-out удаляет текущую сессию и cookie sid, возвращая пустой ответ 204.
POST /api/directory?path=docs%2F создаёт пустую папку и возвращает ресурс:
path — родительская папка, name — имя без завершающего /, type — DIRECTORY.
Нужна сессия. Путь новой папки обязан оканчиваться на /, корень создать нельзя.
Невалидный путь — 400, отсутствие сессии — 401, отсутствие родителя — 404,
существующая папка — 409. Файл docs и папка docs/ могут сосуществовать.
GET /api/resource?path=docs%2F возвращает информацию о папке без поля size.
Для файла ответ содержит размер в байтах; тело файла не скачивается.
Ошибки: 400 — невалидный путь, 401 — нет сессии, 404 — ресурс отсутствует,
500 — неизвестная ошибка. Просмотр содержимого и остальные операции — следующие блоки.
В shared добавлены схемы имени ресурса, пути файла, папки и ресурса,
а также directoryOrRootPathSchema для листинга корня и загрузки в корень.
normalizeAndValidatePath сохраняет корректный путь без изменений и отклоняет
опасные сегменты. Она не декодирует URL. Серверный keyPrefix учитывается только
для проверки лимита 1024 байта UTF-8 и не попадает в возвращаемый путь.
StorageService строит ключи из userId и проверенного пути под серверным префиксом.
Он умеет проверять существование файла или маркера папки через HeadObject;
404 означает отсутствие ресурса, остальные ошибки не подменяются ответом «не найдено».
StorageService создаёт пустую папку нулевым объектом-маркером с завершающим /.
If-None-Match защищает маркер от перезаписи при конкурентном создании.
Бизнес-проверки создания папки находятся в ResourcesService, детали маркера — в StorageService.
GET /api/directory?path= возвращает содержимое корня, а path=docs%2F — папки docs/.
Ответ содержит только непосредственных детей; пустая папка возвращает [], отсутствующая — 404.
S3-страницы объединяются в один ответ, маркер самой папки скрыт.

DELETE /api/resource?path=docs%2F рекурсивно удаляет папку; путь без завершающего
слеша удаляет только файл. Успех — 204 без тела, отсутствующий ресурс — 404.
Удаление папки не атомарно: при сбое часть объектов может уже исчезнуть.
Маркер самой папки удаляется последним, чтобы после сбоя в пачке можно было повторить запрос.

POST /api/resource?path= принимает multipart/form-data с файлами в поле files.
Имя части может содержать относительный путь, например `Папка/Отчёт.txt`.
Ответ 201 содержит только загруженные файлы. При конфликте (409) или превышении
лимитов (400) API откатывает созданные запросом файлы и пустые промежуточные папки.
Если само хранилище недоступно при откате, API возвращает 500 и пишет ошибку в журнал;
часть объектов может остаться. Браузер не отправляет пустые папки при выборе директории.

POST /api/resource/move?from=old&to=new переименовывает ресурс или меняет его
родителя. Операция не атомарна: сначала копируются все объекты, затем удаляются
исходные. Если копирование прервалось, исходники остаются целыми. Проверьте
назначение и удалите частичную копию перед повтором. Если сбой произошёл во время
удаления, полная копия уже есть: проверьте её и удалите оставшиеся исходники.
Не запускайте параллельные изменения того же дерева во время перемещения.

GET /api/resource/download?path=docs%2F скачивает папку как ZIP, путь без
завершающего слеша скачивает файл. Архив собирается потоком, включает пустые
папки и хранит пути относительно скачиваемой папки.

GET /api/resource/search?query=report ищет подстроку в имени файла или папки
без учёта регистра. Поиск линейно сканирует ключи текущего пользователя в S3;
найденные ресурсы сортируются по полному пути. Отдельного индекса поиска нет.
Известное ограничение SeaweedFS 4.48: запись файла с именем уже существующей
одноимённой папки может вернуть 409, хотя контракт допускает оба ресурса.

При `SWAGGER_ENABLED=true` API публикует Swagger UI на `/api/docs` и JSON на
`/api/docs-json`. После изменения API выгрузите JSON и перегенерируйте типы:

```powershell
curl.exe --noproxy "*" --fail http://127.0.0.1:3000/api/docs-json -o apps/web/openapi.json
pnpm --filter @app/web api:generate
```
В shared доступны usernameSchema, passwordSchema, credentialsSchema и тип Credentials.
Регистрация и вход используют credentialsSchema через StandardSchemaValidationPipe.
Подключение к React-формам — следующая задача фронтенд-этапа.

Тесты UsersService требуют запущенного Docker Engine. Testcontainers создаёт
отдельный PostgreSQL-контейнер, применяет миграции и удаляет контейнер после тестов.
Локальная база из Compose в этих тестах не используется.

Тесты сессий запускают отдельный Redis через Testcontainers. Они проверяют cookie,
TTL, восстановление сессии после пересоздания Nest и работу за HTTPS-прокси.
Тестовый контроллер сессий не включается в production-сборку.
HTTP-тесты папок используют отдельный Redis и подменённый StorageService.
Тесты StorageService отдельно проверяют команды SDK и настоящую условную запись
на временном SeaweedFS. Локальные файлы разработчика не затрагиваются.

Тяжёлый тест передачи 2 ГиБ включается отдельно. Он использует временный контейнер,
сверяет SHA-256 и размер скачанного файла, печатает исходный и пиковый RSS процесса.
Проверяется StorageService; это не заменяет прогон через HTTP и nginx.

```powershell
$env:RUN_LARGE_STORAGE_TEST='true'
pnpm --filter @app/api exec vitest run src/storage/storage.integration.spec.ts -t 'streams 2 GiB'
Remove-Item Env:RUN_LARGE_STORAGE_TEST
```

Полный прогон через HTTP с отдельным процессом API:

```powershell
pnpm --filter @app/api verify:large-http
```

Сценарий поднимает временные PostgreSQL, Redis и SeaweedFS, применяет миграции,
регистрирует тестового пользователя, передаёт 2 ГиБ через multipart и скачивает
файл потоком. RSS API измеряется отдельно от клиента; проверяется SHA-256.
Результат сохраняется в `apps/api/verification/large-http.json`.
После завершения временные контейнеры удаляются, локальный Compose не используется.

Анонимные запросы не создают cookie и записи Redis. Регистрация пересоздаёт
идентификатор сессии, записывает userId в Redis и устанавливает cookie sid.
Ответ 201 содержит только username. Ошибки: 400 при невалидном вводе, 409 при
занятом имени, 500 при неожиданном сбое.
PostgreSQL и Redis не участвуют в одной транзакции: если аккаунт создан, а запись
сессии не удалась, API вернёт 500, но аккаунт останется. После восстановления
Redis нужно войти в созданный аккаунт через POST /api/auth/sign-in.
Вход возвращает 200 с username и новой cookie sid. При неверном пароле и неизвестном
username ответ 401 одинаковый: Invalid username or password. Невалидный формат данных
даёт 400, неожиданный сбой — 500. При успешном входе прежняя сессия удаляется.
Выход требует действующей сессии: без неё — 401. После успешного выхода старая
cookie больше не даёт доступ к /api/user/me. Аккаунт и другие сессии сохраняются.
При отказе Redis удалить запись API возвращает 500 без очистки cookie;
клиент должен показать ошибку и повторить выход после восстановления хранилища.
Для запуска API и HTTP-теста нужны PostgreSQL, Redis и SeaweedFS с бакетом user-files:

```powershell
docker compose up -d
pnpm dev
```

## Prisma и миграции

После запуска PostgreSQL применить миграции и сгенерировать клиент:

```powershell
pnpm --filter @app/api db:deploy
pnpm --filter @app/api prisma:generate
pnpm dev
```

После изменения schema.prisma создать новую миграцию в локальной разработке:

```powershell
pnpm --filter @app/api db:migrate --name describe_change
```

schema.prisma описывает модели. prisma/migrations содержит версионированный SQL.
prisma.config.ts загружает корневой .env для CLI отдельно от Nest.
Сгенерированный клиент в src/generated не коммитится; генерация выполняется перед
сборкой, проверкой типов, запуском разработки и тестами.

Первая миграция добавляет users и уникальный индекс username, не меняя другие таблицы.
Применённые миграции не редактируются. Изменения оформляются новой миграцией.
Удаление users уничтожит аккаунты, поэтому автоматического отката с удалением таблицы нет.
В рабочем окружении ошибка кода исправляется откатом приложения или новой совместимой миграцией.

## Фронтенд

React Router в declarative mode подключён к /sign-in, /sign-up, /files/* и /search.
Реализованы вход, регистрация, стартовая проверка сессии, выход и защита страниц;
списки папок, хлебные крошки, создание, переименование, перемещение и удаление;
загрузка файлов и папок с прогрессом и отменой, поиск с debounce 350 мс и скачивание.
При ошибке формы не закрываются и сохраняют введённые данные.
Пути папок кодируются по сегментам; location.pathname декодируется ровно один раз.
`pnpm --filter @app/web test` проверяет маршруты и преобразование специальных имён.

## Разработка на моках MSW

Создайте `apps/web/.env.local` со строкой `VITE_MOCK_API=true` и запустите
`pnpm --filter @app/web dev`. Worker запускается до рендера React. Демонстрационный
аккаунт: `demo_user` / `demo_pass123`. Это вымышленные данные только для разработки.

Обработчики покрывают все операции API, включая изменения, загрузку и скачивание.
Вымышленные файлы хранятся в памяти только в режиме разработки.
Неизвестные API-запросы в этом режиме блокируются.
Мок-сессия живёт в памяти: перезагрузка страницы сбрасывает её и новые аккаунты.
Это не проверка cookie HttpOnly: реальные сессии проверяются тестами API.

При false или отсутствии флага запросы идут в настоящий API через Vite proxy.
В production динамический импорт MSW удаляется сборкой. Скрипт worker хранится вне
public и обслуживается только dev-сервером, поэтому не копируется в dist.

## HTTP-клиент фронтенда

`apps/web/src/api/client.ts` использует относительные URL и типы OpenAPI.
`ApiError` содержит HTTP-статус и понятное сообщение; статус 0 означает сетевой сбой.
Массив message объединяется строками, HTML вместо JSON не показывается пользователю.
Отменённый запрос не превращается в сетевую ошибку.

TanStack Query подключён к React. При обычном 401 запросы отменяются, кэш очищается,
браузер переходит на /sign-in с returnTo исходного адреса. Неверные данные входа и
начальная проверка user/me не запускают этот переход. Скачивание выполняется обычной
ссылкой после проверки сессии, без получения больших файлов через fetch/blob.

## Проверки фронтенда

```powershell
pnpm --filter @app/web test
pnpm --filter @app/web exec playwright install chromium
pnpm --filter @app/web test:e2e
pnpm --filter @app/api verify:frontend
```

Последняя команда поднимает отдельные тестовые PostgreSQL, Redis, SeaweedFS и API,
запускает браузер против настоящего бэкенда и удаляет временные контейнеры.
Проверяются регистрация, загрузка папки с кириллицей, F5, переименование,
перемещение, содержимое скачанного файла и ZIP, поиск, удаление и выход.

Тот же сценарий можно запустить через nginx после старта полного Compose:

```powershell
docker compose -f compose.full.yaml up --build -d

```

Режим `test:full` подключается к `http://127.0.0.1:8080` и не запускает Vite.
Если меняли `FULL_WEB_PORT`, передайте соответствующий локальный HTTP-адрес
в `FULL_STACK_BASE_URL`. Тест проверяет раздачу страницы nginx, флаги сессионной
cookie и её удаление после выхода. Каждый прогон создаёт нового тестового
пользователя; запускайте его на локальном тестовом стеке.

## Docker-образ API

Собирайте из корня репозитория: API использует общий lockfile и пакет `@app/shared`.

```powershell
docker build -f apps/api/Dockerfile --target runtime -t cloud-storage-api:local .
docker build -f apps/api/Dockerfile --target migrator -t cloud-storage-migrator:local .
docker run --rm --entrypoint id cloud-storage-api:local -u
```

Последняя команда должна вернуть UID `1000`: API запускается от пользователя `node`.
В `runtime` копируются только собранные пакеты и production-зависимости из
зафиксированного lockfile. `migrator` запускает `prisma migrate deploy` отдельно.
Перед запуском передайте переменные окружения; внутри сети Compose адреса базы,
Redis и S3 должны указывать на имена сервисов. Корневой `.env` исключён из
контекста сборки и в образ не копируется. Запуск обоих образов с зависимостями
будет оформлен в полном Compose.

## Docker-образ фронтенда

```powershell
docker build -f apps/web/Dockerfile -t cloud-storage-web:local .
```

Первая стадия собирает Vite, вторая переносит только `dist` в nginx. Контейнер
ожидает `api:3000` в своей Docker-сети. `/api/...` передаётся в Nest с исходным
путём; `/files/...` и другие маршруты SPA отдают `index.html`. Отсутствующий
файл из `/assets/` возвращает 404. Хешированные ресурсы кэшируются на год.

`NGINX_CLIENT_MAX_BODY_SIZE` задаёт лимит всего multipart-запроса, по умолчанию
`501g`: 100 файлов по 5 ГиБ и запас на оформление частей. При настройке своего
лимита учитывайте размер файла, количество файлов и служебные байты multipart.
Ограничения на отдельный файл и количество по-прежнему проверяет API.

Запросы и ответы `/api/` проксируются без буферизации. Таймауты чтения и записи
в 300 секунд ограничивают паузу между операциями ввода-вывода, поэтому активная
передача может длиться дольше. В полном Compose для API нужен `TRUST_PROXY=true`;
`COOKIE_SECURE=true` включается только при работе через HTTPS.

## Полный локальный Compose

Из корня репозитория, с заполненным `.env`:

```powershell
docker compose -f compose.full.yaml up --build -d
docker compose -f compose.full.yaml ps -a
```

Откройте [http://127.0.0.1:8080/](http://127.0.0.1:8080/). Порт можно изменить
через `FULL_WEB_PORT`. Наружу опубликован только nginx; API обращается к базе,
Redis и SeaweedFS по именам сервисов внутри сети Compose. Для локального HTTP
API использует `TRUST_PROXY=true` и `COOKIE_SECURE=false`.

Первый запуск готовит схему PostgreSQL и бакет `user-files` автоматически:
`migrator` ждёт здоровый PostgreSQL, а `s3-init` ждёт S3 и создаёт бакет,
если его нет. Оба контейнера должны завершиться с кодом 0. API стартует после
них и Redis; nginx ждёт, пока API начнёт отвечать. Логи этапов:

```powershell
docker compose -f compose.full.yaml logs migrator s3-init api web
```

`FULL_DATABASE_URL` нужен, если пароль содержит спецсимволы URL: передайте URI
с закодированным паролем и хостом `postgres`. По умолчанию URL формируется из
`POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB`.

У полного стека отдельный проект и volumes `cloud-storage-full_*`; существующие
данные из `compose.yaml` не подключаются. `docker compose -f compose.full.yaml down`
останавливает стек и сохраняет volumes. Этот файл предназначен для локального
запуска и e2e, конфигурация VPS будет отдельной.

## Деплой на VPS

Для Linux с Docker Engine и Compose v2 используйте `compose.prod.yaml`. На VPS
работают nginx, API, PostgreSQL и Redis. Файлы хранятся во внешнем S3, а схема
БД обновляется отдельным запуском мигратора перед запуском новой версии API.

1. Загрузите нужную ревизию репозитория. На VPS скопируйте
   `.env.production.example` в `.env.production` и ограничьте доступ к файлу
   командой `chmod 600 .env.production`.
2. Задайте отдельные пароль PostgreSQL и `SESSION_SECRET` (например, отдельный
   `openssl rand -hex 32` для каждого). В `DATABASE_URL` используйте хост
   `postgres` и тот же пароль, закодированный для URL при необходимости.
3. У провайдера создайте приватный бакет `user-files`. Впишите HTTPS endpoint,
   регион, ключи и нужное провайдеру значение `S3_FORCE_PATH_STYLE`. Ключу
   нужны права на проверку бакета, листинг и операции с объектами, включая
   multipart upload. При старте API проверит доступность бакета.

```bash
docker compose --env-file .env.production -f compose.prod.yaml --profile deploy build api web migrator &&
docker compose --env-file .env.production -f compose.prod.yaml up -d --wait postgres redis &&
docker compose --env-file .env.production -f compose.prod.yaml run --rm migrator &&
docker compose --env-file .env.production -f compose.prod.yaml up -d --wait api web
```

По умолчанию nginx доступен только на `127.0.0.1:80` VPS. Для проверки по HTTP
используйте SSH-туннель, например `ssh -L 8080:127.0.0.1:80 user@server`, и
откройте локальный порт 8080. Для временной публичной HTTP-демонстрации
можно указать `WEB_BIND_ADDRESS=0.0.0.0`. PostgreSQL, Redis и API не публикуют
порты. Для публичного использования с реальными учётными данными настройте
HTTPS и включите `COOKIE_SECURE` в конфигурации API после настройки TLS.

После запуска проверьте `ps` и `logs api web`, открытие вложенного URL после F5,
регистрацию и вход, флаги cookie, загрузку и скачивание. Без сессии запрос
`GET /api/user/me` должен вернуть 401 через nginx. Swagger в production отключён.
Перед обновлением сохраняйте резервную копию БД и сохраняйте volumes. При сбое
миграции исправьте причину до запуска нового API. Откат кода возможен только
при совместимости предыдущей версии API с уже применённой схемой.
