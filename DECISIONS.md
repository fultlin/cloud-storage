# Архитектурные решения

## 012. Общая валидация путей без исправления опасного ввода

Решение: схемы путей в shared используют одну базовую Zod-проверку.
normalizeAndValidatePath выбирает контекст файла, папки, ресурса, имени или папки/корня.
Корень разрешается только явным выбором directory-or-root. Пути не декодируются,
не обрезаются и не приводятся к другому регистру или форме Unicode.
Недопустимые сегменты отклоняются, а не схлопываются.

Альтернативы: Node path.normalize или повторный decodeURIComponent.

Причина: они меняют смысл пользовательского пути и могут скрыть попытку обхода.
Лимит сегмента считается в кодовых точках Unicode, ключа — в байтах UTF-8.
Сервер передаёт доверенный keyPrefix для проверки общего размера ключа;
префикс не добавляется к результату и не раскрывается в сообщениях об ошибках.
Непарные суррогаты отклоняются, чтобы UTF-8-кодирование не заменяло разные входы
одним и тем же символом замены.

Используется стандартный TextEncoder, доступный и в браузере, и в Node.
В отличие от начальной настройки из решения 007, shared подключает DOM-декларации
TypeScript для этого API, без runtime-зависимости от DOM или модулей Node.

Основание: разделы 5, 7, 8.6 и 10.1 ТЗ.

## 011. Завершение текущей сессии

Решение: защищённый POST /auth/sign-out вызывает SessionsService.end.
Сначала ожидается callback destroy из express-session, затем clearCookie удаляет sid.
Атрибуты cookie централизованы и одинаковы при создании и удалении; maxAge передаётся
только при создании. Успешный ответ — 204 без тела.

Альтернатива: удалить только cookie или очистить её до подтверждения удаления Redis.

Причина: старая cookie должна потерять силу на сервере, а не только исчезнуть в браузере.
При ошибке Redis возвращается 500 без ложного подтверждения выхода.
Удаляется только текущая сессия, аккаунт и сессии других устройств не затрагиваются.

Основание: разделы 7, 8.3 и 10.2 ТЗ.

## 010. Глобальный guard и текущий пользователь

Решение: AuthModule регистрирует AuthGuard через APP_GUARD. Маршруты закрыты
по умолчанию; только sign-up и sign-in помечены @Public. Guard проверяет положительный
целочисленный userId из сессии. Параметр-декоратор CurrentUserId использует ту же проверку.
GET /user/me читает пользователя из PostgreSQL по этому id и возвращает только username;
отсутствующая запись пользователя означает 401.

Альтернатива: ставить @UseGuards на каждый защищённый контроллер.

Причина: новый эндпоинт нельзя случайно оставить публичным. Идентификатор из query,
тела или заголовков не используется. Проверка сессии и извлечение id централизованы.

Основание: разделы 7, 8.3 и 10.2 ТЗ.

## 009. Регистрация с пересозданием сессии

Решение: AuthController валидирует тело общей credentialsSchema через глобальный
StandardSchemaValidationPipe, вызывает UsersService и затем SessionsService.start.
start оборачивает regenerate и save в Promise, записывает userId в новый req.session
и ожидает сохранения перед ответом 201. При ошибке сохранения новая сессия уничтожается.
Ответ содержит только username, неожиданные ошибки обрабатывает стандартный Nest-фильтр.

Альтернатива: сохранить прежний идентификатор сессии или ответить до сохранения Redis.

Причина: защита от session fixation и отсутствие ложного успеха при сбое store.
Вход использует тот же SessionsService.start после проверки пароля;
при неизвестном username и неверном пароле возвращается одинаковый ответ 401.
Создание пользователя и запись сессии не атомарны между PostgreSQL и Redis;
если второй шаг не удался, аккаунт остаётся и доступен через последующий вход.

Основание: разделы 7, 8.2, 8.3 и 10.2 ТЗ.

## 008. Сессии Redis и единая настройка HTTP

Решение: SessionsService создаёт Redis-клиент и middleware express-session.
Соединение открывается в onModuleInit до приёма HTTP-запросов, закрывается
при остановке Nest. Повторные попытки подключения ограничены, очередь команд
при отключённом Redis запрещена. Middleware подключается через app.use.
configureApp используется в main и тестах с одинаковым префиксом /api и trust proxy.

Альтернатива: MemoryStore или отдельная настройка middleware в каждом тесте.

Причина: сессии переживают перезапуск API; конфигурация тестов соответствует запуску.
Cookie sid подписана, HttpOnly, SameSite=Lax, Secure из env. В Redis сохраняется userId
и служебная информация cookie. saveUninitialized=false не создаёт анонимные сессии,
resave=false избегает лишних записей. rolling=true обновляет cookie при активности,
согласованно с продлением TTL в connect-redis. Срок берётся из SESSION_TTL_SECONDS;
cookie использует миллисекунды, Redis — секунды.
TRUST_PROXY=true доверяет одному ближайшему прокси; false отключает доверие.

Основание: разделы 4, 8.3 и 10.2 ТЗ.

## 007. Общий контракт регистрации и входа

Решение: packages/shared экспортирует Zod-схемы username, password и credentials,
а также выведенный из схемы тип Credentials. Регистрация и вход используют один контракт.
Username не обрезается и не переводится в нижний регистр: запрещённый ввод отклоняется.
Password сохраняется без преобразований. Дополнительные поля объекта удаляются Zod.

Альтернатива: отдельные правила в API и формах React.

Причина: правила раздела 7 определены один раз. Runtime-зависимость shared — только Zod.
Тесты находятся вне src и не входят в dist; Node-типы подключены только для проверки тестов.
skipLibCheck отключает проверку внешних деклараций Zod, использующих URL,
сохраняя проверку исходников shared без глобальных типов Node и DOM.

Основание: разделы 5, 7 и 10.1 ТЗ.

## 006. Хеширование паролей Argon2id

Решение: UsersService использует argon2 с Argon2id, memoryCost 65536 KiB,
timeCost 3 и parallelism 4. Библиотека генерирует случайную соль и включает
параметры и соль в строку хеша. Проверка выполняется через verify.

Альтернатива: bcrypt с дополнительным ограничением пароля до 72 байт UTF-8.

Причина: Argon2id не требует bcrypt-ограничения в 72 байта для Unicode-паролей.
Сервис возвращает только id и username, не раскрывая passwordHash.
Уникальность username гарантирует PostgreSQL; P2002 преобразуется в ConflictException.
Неизвестный username и неверный пароль дают одинаковый результат null.

Доказательство: интеграционные тесты через Testcontainers с настоящей PostgreSQL
и prisma migrate deploy, включая одновременную регистрацию одинакового имени.

Основание: разделы 8.2, 8.4 и 10.2 ТЗ.

## 005. Prisma 7 и жизненный цикл подключения

Решение: генератор prisma-client выпускает TypeScript в src/generated/prisma
с ESM и импортами .js. Nest компилирует его вместе с приложением.
URL БД находится в prisma.config.ts; runtime-клиент использует PrismaPg.
PrismaModule экспортирует один PrismaService, который подключается при инициализации
и закрывает пул при уничтожении модуля.

Альтернативы: отдельный клиент в каждом сервисе или создание таблиц без миграций.

Причина: один управляемый пул соединений, воспроизводимая схема и совместимость
с NodeNext. Уникальность username гарантируется индексом PostgreSQL.
Миграция только добавляет users; автоматического удаления таблицы для отката нет.

Основание: разделы 5 и 8.4 ТЗ.

## 003. Валидация окружения при старте

Решение: ConfigModule получает Zod-схему через validationSchema. Тип Env
выводится из результата схемы; приложение получает значения через ConfigService.
Путь к корневому .env вычисляется относительно app.module, а не текущей папки терминала.
В контейнере переменные могут передаваться без .env через окружение процесса.

Альтернативы: прямое чтение process.env или отдельный ручной валидатор.

Причина: неверные настройки останавливают запуск, строки boolean разбираются
явно, типы и проверка значений описаны одной схемой. Серверная конфигурация
остаётся в API и не экспортируется в браузерный shared.

Основание: раздел 8.1 ТЗ.

## 001. Общий пакет в pnpm workspace

Решение: приложения `@app/api` и `@app/web` используют локальный пакет
`@app/shared` через зависимость `workspace:*`.

Альтернативы: отдельные репозитории или копирование схем в каждое приложение.

Причина: общие схемы и типы живут в одном месте, а workspace-протокол требует
локальный пакет и исключает подмену этой зависимости пакетом из реестра.

Основание: раздел 5 ТЗ.

## 002. Инициализация приложений

Решение: официальные шаблоны Nest CLI 12 (ESM/Vitest) и create-vite (React TypeScript).
TypeScript 6.0.2 используется во всём workspace, как в сгенерированных шаблонах.

Альтернатива: вручную собранный каркас или TypeScript 7 без проверки совместимости.

Причина: используем стартовые настройки генераторов; oxlint вынесен в корень.
В разработке Vite проксирует /api без удаления префикса на NestJS, сохраняя один origin.

Основание: разделы 4, 5 и 8.0 ТЗ.

## 004. Локальная инфраструктура через Compose

Решение: PostgreSQL, Redis и SeaweedFS запускаются в отдельных контейнерах;
API и web остаются локальными процессами. Теги образов фиксированы.
Данные каждого сервиса хранятся в отдельном именованном volume.
Redis использует AOF, SeaweedFS хранит данные и метаданные filer в /data.
S3-ключи передаются через env; бакет создаётся отдельной административной командой.

Альтернатива: установка сервисов на Windows или контейнеризация приложений уже сейчас.

Причина: воспроизводимая инфраструктура без усложнения отладки приложений.
Порты опубликованы только на 127.0.0.1. Полный стек с nginx добавим на этапе деплоя.

Основание: разделы 8.5 и 11 ТЗ.
